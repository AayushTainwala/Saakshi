The owner tested the SOS page on his iPhone on 6 Nov 2026, found two bugs and redesigned the page. His decisions are recorded in `docs/SPEC.md` (sections 4, 5 and 6, marked "owner, 6 Nov 2026"). This brief turns them into work, in **parts a builder takes one at a time**. Read `CLAUDE.md` first, then `docs/SPEC.md` sections 4–6, `docs/spec/evidence-bundle.md` (0.9) and `docs/BUILD_HANDOFF.md` ("Round 2").

Where the SPEC says **built so**, that is the review session's detail for the owner to confirm. Build it, and list it in your pull request under "Built so, please confirm".

## How to work

- **One builder per part, one pull request per group**, in the order below, each from the latest `main`. Branch names `round-2/<group>` (for example `round-2/1-3-sos-swipes`).
- **Parts and who may run together.** Part 1 first. **Group 3.1 (a documents-only pull request) may start at the same time as Part 1**: it needs the owner's review before any Part 3 code, and starting it early gets that review done. Parts 2 and 3 can then run as two builders together. Part 4 last.
- Every group needs: tests for the logic; typecheck, lint and tests green; both native builds green when native code changes; `docs/BUILD_HANDOFF.md` updated (the "Round 2" section: what was done, what was found, what was not verified); and **plain test steps for the owner** in the pull request description, written for someone who is not a software engineer.
- Every user-facing string goes through i18n in English and Hindi. Mark new wording `NEEDS OWNER REVIEW` in the handoff. Anything legal is marked as such; do not write a legal claim of your own.
- Never hand-edit `ios/` or `android/`. Check a dependency's licence before adding it (MIT, BSD, Apache, ISC: yes; GPL, AGPL, LGPL: no). No analytics, advertising or crash-reporting SDK.
- Questions for the owner go in the handoff as `- [ ] (Round 2) question`, with your recommendation. Do not change scope without him. If something in this brief turns out to be impossible on a platform, stop and report it rather than building a workaround; the owner has decided against workarounds that weaken a promise.
- **Wording promise.** Nothing in the app says that recording or sharing "cannot be stopped". It says it can only be stopped in Saakshi with the secret code (SPEC 5.4).
- The wording review of all text is a separate later round; do not hold work for it.

## 1.2 The secret code, and Settings

**The secret code** (SPEC 5.3). A new module `src/modules/secretcode` behind its `index.ts`. Other modules call it to ask "is a code set" and to require it before stopping something; nothing else knows how it is stored.
1. **Four digits.** Set, change and remove in Settings. Changing or removing asks for the current code. Refuse obviously guessable codes (one digit repeated, straight runs up or down) with a plain reason (built so).
2. **Stored as a salted hash** in the phone's secure storage (iOS Keychain, Android Keystore-backed storage), never in the preferences file, never in a log.
3. **Waits grow after each wrong try** (built so): two wrong tries cost nothing; then 30 seconds, 1, 2, 5, 15 and 30 minutes, and 1 hour from there. The count and the end of the wait survive closing the app and restarting the phone. The code screen shows the wait in plain words.
4. **Reset with the phone's own passcode** (the phone's lock screen credential, through the platform's authentication prompt), **only while nothing is running** (no body-cam, Pocket recording, live location or "My phone is being taken"). While something runs, the code screen offers no reset (built so: otherwise whoever holds the phone and its passcode could reset the code and switch the protection off). Report in the handoff what the platform's prompt allows (for example whether it also accepts a face or fingerprint when those are enrolled).
5. **A code screen used by everyone:** `requireSecretCode({ reason })` opens one full-screen code pad and resolves when the right code is entered or the user backs out. If no code is set, the Stop controls ask the user to set one first, and until a code is set "My phone is being taken" cannot be started (the swipe explains why and offers to set it).
6. **Tests:** hashing and verification, the wait schedule (with a fake clock), persistence across restarts, no reset while something runs, the refused codes, and that the visible state follows the stored state.

**Settings** (SPEC 5.8). The Settings tab gains, above the existing items:
- **Trusted contacts** (moved from the SOS tab). Each person keeps the three ticks and gains **how they are reached**: SMS (default) or the Saakshi app. In this part only SMS can be chosen; the Saakshi app option appears in group 3.3. Telegram and email are not shown.
- **Live-location length**: choices 1, 4, 8 and 24 hours; **default 4 hours**.
- **Secret code** (above).
- **Quick trigger**: the setup instructions and toggles of group 1.3.
- The existing items (language, details for certificates, export folder) stay.

Existing users' contacts, ticks and settings are kept (migration test).

# Part 3: Saakshi-to-Saakshi, and the silence alarm

Needs the owner's Apple push key and Google notification service (his guide) before the server and push can be tested end to end. Group 3.1 does not.

## 3.1 The protocol, written down first (documents only)

Write `docs/spec/alerts.md` before any code. **It needs the owner's review before Part 3's code is merged**: it fixes what our server can read, and he is a data-privacy lawyer. Open it as a documents-only pull request; the review session will not merge it.

It must settle, with reasons and the alternatives you rejected:
1. **Identities without accounts.** What keys each install makes (key agreement and signing), where they are kept, and how a lost or replaced phone is dealt with.
2. **Pairing.** A QR code that each phone shows and the other scans (two scans, one each way), what it holds (public keys, the address of the mailbox, a one-time secret that lets the other side write to it), how the owner and the contact check they paired with the right person (for example a few words both phones show), how pairing is undone, and what happens when a contact's phone is replaced.
3. **Sending an alert.** The sender encrypts to each Saakshi-app contact; the server stores the ciphertext until fetched or expired, and sends a **push** (Apple's push service and Google's notification service, called **directly from our Supabase edge function**, not through a third-party push service; built so). The notification carries **nothing readable**: only that Saakshi has something. Use iOS's time-sensitive interruption level; note that Critical Alerts need Apple's approval and go on the release checklist.
4. **What our server can read.** A table: the push addresses of paired phones, ciphertext sizes and times, the live-share records it already holds for SMS contacts. Everything else must be unreadable to it. State where the design reads more than the owner asked for (for example the silence alarm below) and the alternative.
5. **Positions to Saakshi contacts** are part of the alert and are **end-to-end encrypted** too, throttled sensibly; the live link for SMS contacts stays as it is.
6. **Retention.** How long ciphertext waits (a week at most), what is deleted when a share ends, what is deleted when a pairing is undone.
7. **The silence alarm** (3.5): the heartbeat, the server job, and how a contact who has the app is warned without the server reading more than it must. Two designs to weigh, with a recommendation: (a) the phone leaves, with every check-in, a fresh end-to-end encrypted "silence warning" for each contact, which the server releases when the check-ins stop; (b) the server sends a content-free push, and the contact's app shows the share's last position the way the live page does for SMS contacts (readable by our server). Built so, unless you find a reason against: (a) if it is feasible within the battery and size budget, else (b), with the cost of (b) written out.
8. **Abuse.** Rate limits per mailbox and per sender, what a stranger with the public key can do, how a contact blocks a sender.
9. **Privacy-policy facts** the owner will need (what passes through us, for how long), in the same form as Stream B's list for live location.
10. **Libraries** (key agreement, authenticated encryption), their licences (no GPL, AGPL or LGPL) and how they are audited.

1. Register for notifications with the platform's own token (not a third-party push service), ask for notification permission at the right moment (the walkthrough, group 4, or here if the walkthrough is not built yet), and handle the notification.
2. **Received-alerts page** (SPEC 5.6): who has alerted you; their locations with times on a **map** (live, or the last five to ten); and the link to their recordings. Open from the notification and from a list in the SOS tab.

Until he answers, build the list with "open in Maps".
4. Tests with a second simulated device: pair, alert, receive, decrypt, map points. The owner will test it with a friend's phone and the TestFlight build at the end of the round; write those steps.

## 3.5 The silence alarm

1. **Heartbeat.** While "My phone is being taken" or any location share is on, the phone checks in with the server about every 30 seconds, by its own call, independent of movement (a phone standing still sends no new position). It must survive the screen being locked on both platforms. Report the battery cost and what iOS allows when the app is in the background.
2. **Server job** (a cron job, as for expiry): a share whose last check-in is more than about 2 minutes old fires once. A warning to Saakshi-app contacts by push, per 3.1; the live page, for SMS contacts, shows the warning (add it to `web/live/index.html`, English and Hindi): last location, time, battery level, the link to the recordings, and the sentence that the phone has **stopped reporting, not that anything has happened to the person** (built so).
3. **"Reporting again."** When check-ins resume, the page and the app contacts are told (built so), so that a tunnel does not read as an emergency.
4. **Honest limits in the handoff:** SMS contacts get no text (our server sends no SMS: a gateway costs money and needs India's DLT registration); only those who open the link see the warning. The owner should see this clearly.
5. **Start sharing before anything happens.** Share my location is the way (SPEC 5.7); the walkthrough points to it.
6. Tests: the job's timing with a fake clock, once only, resume, both viewers, the heartbeat's start and stop in every mode, and that stopping with the secret code stops the heartbeat and does not fire the alarm.

# Part 4: the first-open walkthrough

Built last, so it sets up everything the earlier parts built. Needs the research in `docs/research/power-off-locks.md` for the phone-setup pages.

1. **Five to seven pages** (SPEC 5.9): language; what Saakshi does; the secret code; trusted contacts and how each is reached; the phone's own protections; the quick trigger; the certificate profile. Each page **introduces the feature and sets it up on the same page**. Permissions (contacts picker, location, notifications, camera for pairing) are asked at the step that needs them, not at launch.
2. **"Skip for now" on every step.** Nothing in the app is blocked by skipping, except "My phone is being taken", which needs the secret code (it offers to set it when swiped). **Call 112 and the camera work from the first screen.**
3. **The phone's protections page** (SPEC G5, "Phone setup"): passcode only, Face ID and fingerprint off; iPhone: Control Center off on the Lock Screen; the phone's own Emergency SOS (iPhone in India: side button three times; Android 12 and later: power button five or more times, not working with Battery Saver on); iPhone: Find My, "findable after power off" and sharing with a trusted person; and the maker's own "require password to power off" where it exists, with the steps for the phone in the user's hand (detect the maker; show the steps that apply, from the research). Wording that states a fact about a maker's setting is only used where the research found a primary source; otherwise it says "check your phone's settings" and gives the path as reported, marked unconfirmed in the handoff.
4. **Guided Access** is not in the walkthrough (unproven; on the phone-test list).
5. **Start sharing before risky stretches:** a page or a card that explains Share my location for walking home late, cabs and protests, and that it is what lets the silence alarm cover them.
6. **Run it again** from Settings.
7. Tests: the steps' order and skip behaviour, state saved when the user leaves half-way, and that permissions are not asked before their step.
